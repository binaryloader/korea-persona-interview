# ADR-001: 멀티턴 + 인터뷰 종료 후 단일턴 구조화 요약 채택

- 상태: Accepted
- 일자: 2026-05-02
- 결정자: dev-planner(설계 합의), 프로젝트 오너(승인 권한)
- 관련 문서: `docs/prd/korea-persona-interview.md` §5.1, §5.3, `docs/tdd/korea-persona-interview.md` §7

## 1. 컨텍스트

`korea-persona-interview` 도구는 한국인 합성 페르소나 1명에게 사업 아이템 관련 질문 N개를 던지고 정량/정성 리포트를 생성한다. 인터뷰 흐름의 핵심 결정 하나는 모델에게 질문을 어떻게 묶어 보낼 것인가다. 같은 질문 묶음이라도 묶음 방식에 따라 페르소나 일관성, 토큰 사용량, 처리 시간, 후처리 복잡도가 달라진다.

세 가지 후보가 존재한다.

### 1.1. 후보 A: 멀티턴 인터뷰 + 별도 단일턴 구조화 요약(2단계 흐름)

질문을 1턴씩 보내고 모델 응답을 messages 히스토리에 누적한다. 인터뷰가 끝나면 별도 system 프롬프트로 같은 모델에게 messages 전체를 입력하고 정해진 JSON 스키마로 구조화 요약을 단일턴 생성한다.

### 1.2. 후보 B: 단일턴 번들

질문 N개를 system 프롬프트에 한 번에 묶어 보내고 모델이 한 번에 모든 답을 자유 서술 + JSON으로 반환한다.

### 1.3. 후보 C: 단일턴 + 사후 요약

후보 B와 동일하게 한 번에 답을 받되, 정성 인사이트만 별도 단일턴으로 생성한다(구조화 요약은 한 번에).

세 후보의 트레이드오프는 아래와 같다.

| 차원 | 후보 A(멀티턴 + 단일턴 요약) | 후보 B(단일턴 번들) | 후보 C(단일턴 + 사후 요약) |
| --- | --- | --- | --- |
| 페르소나 일관성 | 높음(턴마다 system이 보강) | 중(긴 응답에서 후반부 이탈 가능) | 중 |
| 토큰 사용량 | 높음(약 1.8-2.5배) | 낮음 | 낮음 |
| 처리 시간 | 길다(턴 수 × 평균 지연) | 짧다 | 짧다 |
| 후처리 복잡도 | 낮음(턴별 응답 분리 자명) | 높음(자유 서술 분할) | 높음 |
| 자동 follow-up 통합 | 자연스러움(턴 단위 트리거) | 어려움(번들 후 추가 턴 필요) | 어려움 |
| 모델 거부 / drift 격리 | 턴 단위 격리 | 한 답이 오염되면 전부 오염 | 한 답이 오염되면 전부 오염 |
| 디버깅 용이성 | 높음(턴별 로그) | 낮음 | 낮음 |

본 도구의 핵심 가드레일은 자동 follow-up과 페르소나 깨짐 감지(PRD §7.2 Should 상향)다. 두 기능 모두 턴 단위 격리가 필요하다. 짧은 답변 follow-up은 답변별로 트리거되어야 하며, drift 감지도 턴별로 격리되어야 한 응답이 오염되어도 다른 응답은 살릴 수 있다.

또한 PRD §6.1의 처리 성능 목표(100명 30분, 동시성 2 가정)는 100명 × 5질문 × 4초 = 약 33분으로 후보 A에서도 동시성 2면 16-20분 수준이라 SLO를 만족한다.

## 2. 결정

후보 A 채택. 멀티턴 인터뷰로 질문 N개를 1턴씩 보내고, 인터뷰 종료 후 별도 단일턴으로 구조화 요약을 생성한다. 이 결정은 PRD §5.1, §5.3에 이미 반영되어 있고, TDD §7에서 토큰 truncation 정책과 함께 구체화한다.

세부 정책은 아래와 같다.

- system 메시지는 messages[0]에 항상 보존한다(절대 truncate하지 않음)
- 누적 토큰이 8000(`llm.context_budget`)을 초과하면 system을 제외한 가장 오래된 user/assistant 페어부터 제거한다
- 토큰 추정은 한국어 1자 = 1 토큰, 영어 1자 = 0.25 토큰, 그 외 0.5 토큰 휴리스틱으로 한다
- truncation 발동 시 WARN 로그 + `flags.truncated=True`(스키마 추가)
- 구조화 요약은 인터뷰 종료 후 별도 system 프롬프트로 단일턴 호출한다. JSON 파싱 실패 시 1회 retry, 그래도 실패면 `structured_summary=None`
- 단일턴 모드는 `--single-turn` 플래그로만 제공한다(빠른 dry-run, 토큰 절약 목적). v1 기본값은 멀티턴이다

## 3. 결과

### 3.1. 긍정적 결과

- 페르소나 일관성 향상: 턴마다 system이 살아 있어 후반 질문에서도 페르소나가 유지된다. 자체 측정에서 PRD §9 목표(drift 5% 이하) 달성 가능성이 가장 높은 옵션이다
- 자동 follow-up이 자연스럽게 통합된다. 답변 길이 < 20자 또는 모호 키워드 매칭 시 같은 턴 흐름에서 후속 질문 1회 추가
- drift/refusal 감지가 턴 단위로 격리되어 한 응답이 오염되어도 다른 응답을 살릴 수 있다
- 디버깅 용이성: `raw_responses[i]`로 턴별 응답, 지연, retry를 분리해서 볼 수 있다

### 3.2. 부정적 결과

- 토큰/시간 비용 약 1.8-2.5배 증가(질문 5개 기준). PRD §6.1 처리 성능 목표 30분은 만족하지만 여유가 줄어든다
- truncation 정책이 필요해 구현 복잡도가 추가된다(TDD §7)
- 구조화 요약 단일턴 호출이 매 페르소나당 1회 추가된다. 100명 × 1회 = 100회 추가 호출. 평균 4초로 약 6-7분 추가
- 멀티턴 messages 직렬화 시 JSON 크기가 단일턴 대비 약 3-4배. 100명 배치 결과 JSON이 약 5-15MB 수준이 될 수 있다(`outputs/`는 .gitignore 처리되어 저장소 부담은 없음)

### 3.3. 후속 재검토 트리거

본 결정은 아래 조건 중 하나가 발생하면 재검토한다(supersede 후보 ADR 작성).

- PRD §6.1 SLO 위반: 100명 인터뷰 30분 초과가 일관되게 측정되면 후보 C(단일턴 + 사후 요약)로 supersede 검토
- 토큰 비용 과다: 14B 4bit 모델로 한 인터뷰가 평균 8000 토큰을 넘기면(즉 truncation이 자주 발동하면) 단일턴 + 압축 system 프롬프트 조합 검토
- drift 비율이 5% 임계를 만족하지 못하면 페르소나 보강 빈도(매 턴 system 재주입) 또는 멀티턴 + 추가 가드레일로 진화

재검토 시 새 ADR(`docs/adr/{날짜}-multiturn-revision.md`)을 작성하고 본 ADR의 상태를 `Superseded by ADR-NNN`으로 갱신한다(architecture.md §11).

## 4. 대안과 거부 사유

### 4.1. 후보 B: 단일턴 번들

거부 사유는 아래와 같다.

- PRD §7.2 Should인 자동 follow-up과 페르소나 깨짐 감지가 턴 단위 격리를 전제로 한다. 단일턴 번들은 한 응답에 N개 답이 섞여 있어 답별 격리가 어렵다
- 한 답에서 페르소나가 깨지면 전체 응답을 drift로 처리해야 해서 데이터 손실이 크다
- 자유 서술 본문에서 답을 분리하는 후처리(파싱)가 모델 응답 형식에 따라 깨질 위험이 크다

### 4.2. 후보 C: 단일턴 + 사후 요약

거부 사유는 후보 B와 같다. 추가로 사후 요약을 별도 호출해도 1차 응답이 이미 단일턴 번들 형태라 답별 격리 문제가 남는다. 토큰 절감은 있지만 본 도구의 핵심 가드레일과 양립하지 않는다.

### 4.3. 후보 A 변형: 멀티턴 + 매 턴 system 재주입

매 턴마다 system 메시지를 재주입하는 변형은 페르소나 일관성을 더 강화하지만 토큰을 추가로 약 N배 더 소모한다. v1에서는 system을 messages[0]에 1회만 두고 truncation 정책을 적용한다. drift 비율이 5%를 넘으면 v1.1에서 변형을 도입할 수 있다(재검토 트리거 §3.3과 연결).
