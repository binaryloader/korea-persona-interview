# 백로그: v1.1

본 문서는 v1.0 본체에 포함하지 않고 v1.1로 미룬 항목을 모은다. 각 항목은 동기, 영향 범위, 사전 의존성을 짧게 적는다. 우선순위 결정은 v1.0 운영 데이터(실제 사용자 피드백, 비용 패턴, drift 비율)가 모인 뒤 다시 본다.

## 1. 사용자 경험과 신뢰성

### 1.1. resume 옵션(부분 실패 후 재개)

- 동기는 100명 배치에서 30명만 완료되고 exit 3으로 빠진 경우 같은 시드/필터로 처음부터 다시 돌리는 비용을 줄이는 것이다
- 영향 범위는 `src/batch.py` 완료 record 식별 + 누락분 재실행, `main.py` `--resume INTERVIEW_ID` 플래그 + 결과 JSON 머지, 결과 JSON 스키마에 `run_id`/`previous_run_id` 추가다
- 사전 의존성은 결과 JSON에 record 단위 식별자가 안정적으로 부여되어 있다는 점이다(현재 `persona_id` 기반으로 충분)

### 1.2. 진행률 + 부분 결과 streaming 저장

- 동기는 100명 배치 도중 OOM/네트워크 단절로 프로세스가 죽으면 마지막 SIGINT partial save 이후 진행분이 모두 사라진다는 점이다
- 영향 범위는 `src/batch.py` record 단위 increment append, 결과 JSON 포맷 부분 record 안전 직렬화, tqdm 자리 정합이다

### 1.3. streaming 응답(체감 속도)

- 동기는 dry-run에서 응답이 한 번에 떨어지는 대신 실시간으로 흐르면 프롬프트 디버깅이 빨라진다는 점이다
- 영향 범위는 `src/llm_client.py` `stream=True` 분기, `src/interview.py` streaming reducer, `--dry-run` 콘솔 출력이다
- 단일턴/배치는 streaming 도입 가치가 작아 dry-run 한정으로 한정 도입을 검토한다

## 2. 토큰 사용량 최적화

### 2.1. OpenAI Batch API offline 경로

- 동기는 100명 배치를 실시간으로 받을 필요가 없다면 OpenAI Batch API의 24시간 윈도우 전송 경로를 활용해 사용자 provider의 batch 단가 혜택을 받을 수 있다는 점이다(단가 비교는 사용자 본인의 OpenAI 청구 페이지에서 확인)
- 영향 범위는 `src/llm_client.py` Batch endpoint, `src/batch.py` async ↔ batch poll 흐름 분리, 결과 JSON에 `batch_job_id` 추가다
- 사전 의존성은 사용자가 비실시간 결과를 수용한다는 명시적 옵션 즉 `--batch-async` 플래그다

### 2.2. 인사이트 모델 분리(인터뷰는 mini, 인사이트는 4o)

- 동기는 인터뷰 1차 응답은 `gpt-4o-mini`로 충분하지만 정성 인사이트 1회 호출은 `gpt-4o`가 더 깊은 통찰을 준다는 점이다
- 영향 범위는 `src/report.py` insight 호출용 별도 LLMConfig, `config.yaml` `report.insight_model`, CLI `--insight-model` 옵션이다

### 2.3. multi-model A/B 라우팅

- 동기는 같은 페르소나 샘플에 다른 모델을 돌려 응답 품질을 비교하면 모델 선택 의사결정이 빨라진다는 점이다
- 영향 범위는 `src/batch.py` 모델 라우팅 매트릭스, 리포트의 모델별 비교 표, CLI `--model-set` 옵션이다
- 사전 의존성은 cached_tokens 처리가 모델별로 정합하다는 점으로 라운드 A에서 처리 완료다

## 3. 보안과 운영

### 3.1. 시크릿 keychain 연동

- 동기는 macOS Keychain/Linux libsecret/Windows Credential Manager에 키를 저장하면 `.env` 파일이 디스크에 평문으로 남지 않는다는 점이다
- 영향 범위는 `src/config.py` 시크릿 로더에 keyring 라이브러리 도입 또는 OS 명령 호출, README 설치 가이드다
- 사전 의존성은 keyring 라이브러리(또는 동등한 stdlib 우회)의 라이선스/취약점 점검이다

### 3.2. drift 휴리스틱 region/age/gender 축 정밀화

- 동기는 라운드 B 시점에 family_type 축만 같은 문장 단위 정밀 정규식으로 강화됐고 region/age/gender는 여전히 30자 윈도우 단순 토큰 매칭이라는 점이다
- 영향 범위는 `src/interview.py` detect_persona_drift 정규식 묶음 재설계, 회귀 테스트에 false positive/negative 케이스 추가다
- 사전 의존성은 v1.0 실제 사용 데이터에서 false positive/negative가 어느 정도 나오는지 측정한 뒤 진행한다는 점이다

### 3.3. LLM-as-judge drift 보강

- 동기는 휴리스틱이 잡지 못하는 미묘한 페르소나 이탈(말투만 페르소나 같고 내용은 모델 디폴트)도 잡고 싶다는 점이다
- 영향 범위는 `src/interview.py` judge 호출 1회 추가, 비용 측면에서 record당 호출 1건 증가, `report.exclude_judge_drift` 옵션이다
- 사전 의존성은 v1.0 휴리스틱 측정값이 5%를 초과해 추가 가드가 필요하다고 확인된 시점이다

### 3.4. 직업명 영문 화이트리스트

- 동기는 `IT 컨설턴트`, `UX 디자이너` 같은 직업명을 가진 페르소나가 응답에 직업명을 자연스럽게 사용해도 영어 비율 false positive로 drift 판정되는 회귀가 남아 있다는 점이다
- 영향 범위는 `src/interview.py` 영어 비율 계산 시 직업명 토큰 화이트리스트 추가, config 키 `interview.occupation_english_whitelist`다
- 사전 의존성은 v1.0의 페르소나 메타 토큰 제외 기본 동작을 유지한 채 화이트리스트만 추가하는 패치다

## 4. 외부 통합

### 4.1. FastAPI REST API

- 동기는 MCP/CLI 외에 REST API 진입을 원하는 외부 시스템(웹 대시보드, 사내 자동화 등)도 같은 application 계층을 재사용할 수 있다는 점이다
- 영향 범위는 `src/api/` 신규, 의존성 `fastapi`/`uvicorn` 추가, 인증 `X-API-Key` 헤더, 비동기 큐로 `run_batch` 백그라운드 실행이다
- 사전 의존성은 application 계층이 진입점에 독립적이라는 점으로 라운드 C1에서 확인 완료다

## 5. 패키징과 코드 정리

### 5.1. requirements.txt와 pyproject.toml 단일 정본

- 동기는 라운드 C4에서 두 곳을 동시 유지하기로 한 결정을 v1.1에서 정리해 이중 관리 부담을 없앤다는 점이다
- 영향 범위는 `pyproject.toml`의 `dependencies`만 정본으로 두고 `requirements.txt`를 제거 또는 자동 추출로 전환하는 작업이다
- 사전 의존성은 lock 도구가 `pyproject.toml`에서 직접 lock을 생성할 수 있어야 한다는 점이며 uv 0.x 이상에서 가능하다

### 5.2. main.py SRP _run_dry_run 분리

- 동기는 `main.py`의 `_run_dry_run`이 click 콜백 흐름과 인터뷰 시연 출력 두 책임을 갖고 있어 라운드 B6 SRP 분리에서 미뤄둔 항목이다
- 영향 범위는 `src/cli_views.py` 또는 신규 `src/dry_run.py`로 dry-run 출력 책임 이동, `main.py`는 라우팅만 담당한다
- 사전 의존성은 라운드 B6에서 분리한 `console.py`/`cli_views.py` 구조를 그대로 활용한다는 점이다

### 5.3. MlxLLMClient 클래스명 → LLMClient 또는 OpenAIClient

- 동기는 클래스명이 ADR-002 이전의 MLX 백엔드 시절을 그대로 보존하고 있어 백엔드 무관 명칭으로 정리한다는 점이다
- 영향 범위는 `src/llm_client.py` 클래스 rename, import 사이트 약 12군데, 회귀 테스트 patch path다
- 사전 의존성은 관련 PR 1개로 묶어 공개 API 변경 없음을 확인한 뒤 머지한다는 점이다

### 5.4. prompts/ 패키지 sdist 포함

- 동기는 라운드 C4 시점에서 `pip install` 사용자가 `prompts/system_prompt.txt`를 별도로 가져와야 하는 한계를 정리한다는 점이다
- 영향 범위는 `pyproject.toml`의 package-data 설정, `src/interview.py`에서 `importlib.resources`로 읽기, config `interview.system_prompt_path`의 default 변경이다
- 사전 의존성은 사용자가 외부 파일 편집으로 커스터마이징하는 흐름은 그대로 두고 default 경로만 패키지 내부로 옮긴다는 점이다

### 5.5. Anthropic prompt caching cache_control 마커 도입

- 동기는 `AnthropicBackend`가 `cache_read_input_tokens` 토큰 회계는 받지만 시스템 프롬프트에 명시적 `cache_control` 마커를 박지 않아 캐시 hit 비율이 낮다는 점이다. Anthropic은 OpenAI와 달리 명시 마커 기반이다
- 영향 범위는 `src/llm_backend.py`의 `AnthropicBackend.chat`에서 system 메시지 분할 시 정적 prefix에 `{"type": "text", "text": ..., "cache_control": {"type": "ephemeral"}}` 마커를 박는 작업, 가변 부분과 분리, 회귀 테스트 추가다
- 사전 의존성은 시스템 프롬프트 정적/가변 경계가 이미 분리되어 있다는 점이다(라운드 A6에서 처리됨)

### 5.6. 로컬 LLM thinking 옵션 자유 양식 yaml

- 동기는 mlx_lm.server/vLLM이 `chat_template_kwargs`로 thinking 토글을 받지만 본 도구 LlmConfig가 OpenAI 표준 외 필드를 노출하지 않아 사용자가 yaml에서 직접 박을 수 없다는 점이다
- 영향 범위는 `LlmConfig`에 `extra_body: dict` 추가, `MlxLLMClient.chat`과 `AnthropicBackend.chat`에서 request body에 머지, 회귀 테스트다
- 사전 의존성은 free-form yaml dict가 검증 통과하도록 `__post_init__` 정책 정리다

### 5.7. provider별 페르소나 응답 품질 검증 보고서

- 동기는 ADR-003 채택으로 OpenAI/Anthropic/로컬 LLM/MCP sampling 네 경로가 활성화되었지만 페르소나 일관성과 drift 비율은 `gpt-4o-mini`로만 검증된 상태라는 점이다
- 영향 범위는 `tests/manual/quality_validation.py` 신규 작성으로 provider별 100명 페르소나 인터뷰와 메트릭 자동 측정을 수행하고 결과 표를 `docs/quality/{provider}_{model}.md`로 저장한다
- 사전 의존성은 골든 데이터셋 50-100개 정의다. intent 분포가 알려진 페르소나 쌍을 우선 모은다

### 5.8. persona_id 직접 지정

- 동기는 동일 페르소나에 대해 다른 product 또는 다른 questions로 비교 인터뷰를 돌리고 싶을 때 seed와 filter만으로는 동일 표본을 보장하기 어렵다는 점이다
- 영향 범위는 CLI `--persona-ids p-0001,p-0002,...` 옵션, `load_and_sample`에 `persona_ids: list` 분기, 검증된 페르소나 메타 dict 반환이다
- 사전 의존성은 `persona_id`가 데이터셋 row 단위 안정 식별자라는 점이며 현재 dataset의 `uuid` 컬럼을 그대로 쓴다

## 6. 우선순위 가이드

본 백로그는 단순 나열이 아니다. v1.0 운영 데이터를 보고 아래 순서로 검토한다.

- 토큰 사용량 누적이 사용자 운영 부담을 키우면 §2.1 Batch API와 §2.2 인사이트 모델 분리를 우선한다
- 신뢰성 사고가 있으면 §1.1 resume과 §1.2 streaming 저장을 우선한다
- drift 비율 5% 초과가 측정되면 §3.2와 §3.3을 우선한다
- 외부 통합 요청이 들어오면 §4.1을 검토한다
- 코드 정리(§5)는 위 항목 작업 사이의 컨텍스트 전환 비용을 줄이려 묶어서 처리한다
